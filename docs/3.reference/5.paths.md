# Paths and Locking

**The absolute-POSIX path helpers the sessions use, and the lock they take over the path map.**

```ts
import {
  basename,
  dirname,
  isNormalizedPath,
  isPathInside,
  joinPath,
  normalizePath,
  PathLock,
  resolvePath,
  splitPath,
} from "mountx";
```

Both are exported because a driver doing its own path bookkeeping wants the same rules the transports follow — not because a driver has to call them. Every path a driver receives is already normalized.

## Path helpers

Absolute POSIX paths only; `..` clamps at the root, so no input can escape upward out of the mount.

```ts
splitPath("/a/b"); // ["a", "b"]
normalizePath("/a//b/../c"); // "/a/c"
joinPath("/a", "b"); // "/a/b"
dirname("/a/b"); // "/a"
basename("/a/b"); // "b"
isPathInside("/a/b", "/a"); // true
```

### `isNormalizedPath()`

Is this path already in the exact form `normalizePath()` would produce — absolute, no `//`, no trailing `/`, no `.` and no `..`?

```ts
isNormalizedPath("/a/b"); // true
isNormalizedPath("/a//b"); // false
isNormalizedPath("a/b"); // false — not absolute
```

Same answer as `normalizePath(p) === p`, in one pass over the string instead of a split and a rejoin. `normalizePath()`, `dirname()` and `basename()` all ask it first and skip the work when it says yes, so an already-normal path — which is every path a session hands a driver — costs a scan rather than an allocation.

### `resolvePath()`

Normalize and split in one call, for the drivers that want both:

```ts
resolvePath("/a/./b"); // { path: "/a/b", segments: ["a", "b"] }
resolvePath("/"); // { path: "/", segments: [] }
```

`normalizePath(p)` followed by `splitPath(p)` walks the string twice and throws the first array away — and walking a path component by component is what a driver resolving `/a/b/c` against its own tree does on every call. `segments` is a fresh array you own and may mutate.

## `PathLock`

The writer lock over the path map, shared by all three transports' sessions. `RENAME` takes it; `READ`/`WRITE` run outside it — the whole point being that bulk I/O never waits on a rename that is not in its way. 9P holds one per connection rather than one per mount — a rename is serialized against other traffic on the same connection, not against a second client's.
