# Mounting into a VM

**The host serves, the guest mounts. Nothing to install inside the guest.**

A Linux guest already has the clients: `v9fs` and the NFS client are in the kernel. mountx's 9P and NFS servers speak over an ordinary TCP socket, so a driver running on your host shows up as a real folder inside the VM after one `mount` command — no agent to install, no shared-folder daemon, no guest additions.

| VMM                                        | use                        | because                                                                      |
| ------------------------------------------ | -------------------------- | ---------------------------------------------------------------------------- |
| **[QEMU](#qemu)**                          | [9P](/transports/9p)       | its default networking reaches the host with no setup at all                 |
| **[Firecracker](#firecracker)**            | [NFSv4.1](/transports/nfs) | its guest kernel has no 9P client — not a missing option, it is not compiled |
| **[Anything else](#any-other-hypervisor)** | either                     | whichever client the guest kernel has, over whatever network it has          |

Serving needs no privileges on either transport — [that never changes](/guide/quick-start#do-i-need-root). Only the `mount` inside the guest needs root, and root inside a throwaway VM costs nothing.

## QEMU

QEMU's default user-mode networking already routes **`10.0.2.2` to the host's loopback**. That is the whole trick, and it is worth being explicit about what it saves you:

- no tap device, no bridge, no `ip` commands on the host, **no root on the host**
- no `-netdev` configuration — the default `-nic user` is what you want
- the server stays bound to `127.0.0.1`, so nothing on your network can reach the driver

### 1. Serve on the host

```ts [serve.ts]
import { createP9Server } from "mountx/9p";
import { createMemoryDriver } from "mountx/drivers/memory";

const driver = createMemoryDriver();

const server = await createP9Server(driver, { port: 5640 }).listen();
console.log(`serving 9P on 127.0.0.1:${server.port}`);
```

Leave it running. `createMemoryDriver()` is a stand-in — any [driver](/guide/drivers) works, which is the point.

### 2. Boot a guest

Any Linux with `CONFIG_NET_9P`, which is nearly all of them. [Alpine's `virt` image](https://alpinelinux.org/downloads/) is a good tiny one to try it with:

```sh
qemu-system-x86_64 -enable-kvm -m 512 -nographic \
  -cdrom alpine-virt-3.21.3-x86_64.iso \
  -nic user
```

`-nic user` is the default networking, spelled out. Log in as `root` with no password.

### 3. Mount, inside the guest

```sh
mkdir -p /mnt/x
mount -t 9p -o trans=tcp,port=5640,version=9p2000.L 10.0.2.2 /mnt/x
```

That is the entire client side. `ls /mnt/x` is now your driver.

::note
**If the guest has no address yet.** A minimal image may boot with `eth0` down. QEMU's network is `10.0.2.0/24`, so one line is enough to reach the host — the host is on-link, and no default route is needed for the mount itself:

```sh
ip addr add 10.0.2.15/24 dev eth0 && ip link set eth0 up
```

Add `ip route add default via 10.0.2.2` only if you also want the guest to reach the internet.
::

### Why those three options, and no more

- **`trans=tcp,port=`** — 9P over a stream. The mount's _source_ is the address and the port is a separate option, which is why `10.0.2.2` appears with no `:5640` after it.
- **`version=9p2000.L`** — mountx speaks the Linux dialect only, and refuses anything else. Capital `P`.
- **Nothing else is required.** No `modprobe`: `mount -t 9p` auto-loads `v9fs` and `9pnet_fd`. `cache=none` and `access=client` are already the kernel's defaults for `.L`, and mountx's own defaults agree with them.

::caution
**The source must be a dotted-quad IPv4 literal.** The kernel validates a 9P TCP source with `valid_ipaddr4()` — a `sscanf("%d.%d.%d.%d")` and nothing else. No hostnames, and no IPv6. `10.0.2.2` satisfies it; `localhost` and `::1` do not. See [the 9P transport page](/transports/9p#transtcp-for-a-vm-guest).
::

### This is not QEMU's `-virtfs`

Worth separating, because the flag names collide. QEMU has its _own_ built-in 9P server, reached with `-virtfs`/`-fsdev`, and it exports **a directory on your host**. It cannot be pointed at an external 9P server — every `-fsdev` backend is directory-based, so there is no way to hand mountx to `virtio-9p`.

So mountx connects over TCP instead. You give up virtio's shared memory and gain the thing you actually wanted: the filesystem is _your JavaScript_, not a host directory.

### Making it faster

The default `msize` is the kernel's own (128 KiB of payload). Raising it is the knob that matters most for bulk I/O over TCP, on both ends:

```sh
mount -t 9p -o trans=tcp,port=5640,version=9p2000.L,msize=1048576 10.0.2.2 /mnt/x
```

1 MiB is mountx's ceiling and the kernel's `MAX_SOCK_BUF`. See [Tuning](/guide/tuning) for the rest, and mind [`cache=none`](/transports/9p#cachenone) before raising the cache mode: 9P has no invalidation channel, so any cache above `none` is a bet that nothing but the guest changes your driver.

## Firecracker

**Firecracker cannot do 9P, and no option will turn it on.** Two independent reasons, both worth stating because neither is a configuration mistake:

- It emulates **virtio-net, virtio-block and virtio-vsock** (plus balloon and rng) and nothing else. There is no `virtio-9p` device to attach.
- Its published guest kernels ship `# CONFIG_NET_9P is not set` — the client is not compiled in, so even a device would have nothing to talk to.

What those kernels _do_ have is the NFS client, and specifically:

```
CONFIG_NFS_FS=y
CONFIG_NFS_V4=y
CONFIG_NFS_V4_1=y
# CONFIG_NFS_V3 is not set
```

So the transport for Firecracker is **[NFSv4.1](/transports/nfs)** — and NFSv3, which is the older half of mountx's NFS support, is not an option there either. Check your own kernel before assuming, since these are build-time choices:

```sh
# whichever of the two your guest has
zcat /proc/config.gz 2>/dev/null || cat "/boot/config-$(uname -r)"
```

and grep it for `CONFIG_NET_9P`, `CONFIG_NFS_V4_1` and `CONFIG_NFS_V3`.

### Serving

The guest arrives from the tap subnet rather than loopback, so this server has to be told to accept a non-loopback peer:

```ts [serve.ts]
import { createNfsServer } from "mountx/nfs";
import { createMemoryDriver } from "mountx/drivers/memory";

const server = await createNfsServer(createMemoryDriver(), {
  port: 2049,
  allowRemote: true, // the guest is not on loopback
}).listen();
```

::caution
**`allowRemote: true` exports your driver to anything that can reach the socket.** NFS authenticates nothing here. Bind it to the tap address rather than `0.0.0.0`, and treat the network path as the entire security boundary — the same posture [the NFS page](/transports/nfs) describes.
::

### Mounting

```sh
mount -t nfs4 -o vers=4.1,port=2049,proto=tcp,sec=sys,hard,addr=<host-tap-ip>,clientaddr=<guest-ip> \
  <host-tap-ip>:/ /mnt/x
```

`vers=4.1` matters: v4.1 is what mountx implements and what that kernel has. There is no MOUNT program and no rpcbind to run, which is one of the reasons v4 is the easier half to serve into a VM.

### The part that needs root

Firecracker has **no user-mode networking**. Every guest network is a tap device on the host, so unlike the QEMU recipe above, the host side needs `CAP_NET_ADMIN` and a `/dev/net/tun` — one `ip tuntap add` plus an address, done once. That is a property of Firecracker, not of mountx.

::note
**What has been checked, and what has not.** The kernel-config and device facts above are read from Firecracker's own published guest kernels and documentation. mountx's NFSv4.1 server is verified against a real Linux kernel NFSv4.1 client — mount, read, write, `mkdir`, bulk `dd`, rename, unlink and unmount — but that verification was driven from a QEMU guest, because it needs no tap device. The Firecracker-specific tap wiring has not yet been exercised end to end here.
::

## Any other hypervisor

The rule generalises: **serve over TCP, mount with whatever client the guest kernel has.**

- **Cloud Hypervisor, and QEMU with a tap or bridge** — same 9P recipe, with the host's address on that network in place of `10.0.2.2`. It still has to be a dotted-quad literal.
- **WSL2, Multipass, Lima, UTM, VirtualBox, Proxmox guests** — a Linux guest with a route to the host is all this needs. Use 9P when the kernel has it, NFSv4.1 when it does not.
- **macOS guests** — [NFS only](/transports/nfs), on any version: no BSD kernel has a v9fs client.

Two things to get right wherever you land:

- **Bind deliberately.** `createP9Server`/`createNfsServer` bind `127.0.0.1` by default and refuse non-loopback peers. Reaching them from a guest on a real network means `allowRemote: true`, which exports the driver to everything that can reach the socket — neither protocol authenticates anything.
- **The guest is a second client.** Both servers accept more than one connection, but 9P's locks are grant-all and a rename is only serialised per connection. Mounting the same driver from the host _and_ a guest at once is [not the case either transport is designed for](/transports/9p#serving-more-than-one-client).
